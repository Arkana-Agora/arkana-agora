# Módulo 1 — Sistema de Autenticação e Autorização (SPEC-001)

## Overview

**Problema/Motivação:** O SPEC-001 define um sistema completo de autenticação e autorização
(email/senha, Google/Facebook OAuth, magic link, recuperação de senha, refresh com rotação,
logout e ciclo de vida LGPD). As 29 tarefas já viraram issues no GitHub (milestone
**Sprint 1 - Core Features**, label `001-auth`) e devem ser executadas **uma por branch**,
na ordem determinada por este plano.

**O que estamos construindo:** A execução das 29 issues do módulo 1 como elas estão descritas
em `.specs/001-auth/tasks.md` e contratadas nas issues, **mais 3 tasks extras**: T7a (serviço
compartilhado de tokens), T30 (verify-email p/ fechar a verificação) e T31 (VerifyEmailPage +
MagicLinkCallback p/ fechar design §6), com a
**Custom JWT Layer completa do ADR-009 Gate B** (access RS256 15min + refresh rotativo 30d +
`tokenVersion` validado contra Redis + detecção de reuso por família) como o núcleo do backend
em `/api/v1/auth/*`.

**Para quem:** todos os usuários da plataforma (anônimos que se cadastram, usuários
autenticados, e a equipe de desenvolvimento que executa as tasks).

**Nota sobre o estado atual da branch:** a branch atual `#001-auth-instalar-e-configurar-authjs`
(incluindo `dev`) já contém um scaffold de auth do **Sprint 0** (`src/auth/auth.config.ts`,
`src/auth/prisma-adapter.ts`, `src/auth/auth.ts`, handler `[...nextauth]`, `src/proxy.ts`,
páginas `/login` + `/dashboard`, ADR-010, schema com 5 models e migration init). Por decisão
do PO (2026-09-01), este plano trata **cada task como implementação independente nas branches
novas**, reimplementando o que cada issue contratar conforme `design.md`/`04-api/authentication.md`/
ADR-009-010 — usando o scaffold do Sprint 0 como **referência de contrato e sanidade**, não como
entregável presumido de cada issue.

## Proposed Solution

### Arquitetura-alvo (pós-módulo-1)

```
Client (Browser)
  ├── Zustand AuthStore (access token em memória) + Axios interceptor
  │       │ Authorization: Bearer <accessToken>
  ▼
  src/app/api/v1/auth/*          # Custom JWT Layer (ADR-009 Gate B) — MÓDULO NOVO
  │   register, login, magic-link, magic-link/verify, forgot-password,
  │   reset-password, verify-email (T30), refresh (rotação+reuso), logout, account (DELETE),
  │   restore-account
  ▼
  src/auth/*                     # Auth.js v5 (camada de login, ADR-010)
  │   Google OAuth + magic link via /api/auth/* (existente no Sprint 0)
  ▼
  Redis (ioredis)                # validação de tokenVersion + rate limiting
  Prisma (Postgres)              # User, Session, VerificationToken (+ rate-limit in-memory)
```

### Decisões de solução (contratos canônicos a seguir)

- **[S1] Custom JWT Layer** (ADR-009 Gate B, conforme `docs/04-api/authentication.md`):
  - Access token **JWT RS256, 15 min**, payload `{ sub, role, plan, tokenVersion, iat, exp }`.
    Permissões derivadas server-side a partir do `role` — **nunca** vão no payload.
  - Refresh token **opaco, 30 dias**, persistido no model `Session` **com hash SHA-256**
    (`tokenHash`), com `familyId`/`tokenId`/`replacedByTokenId` para **rotação + detecção de
    reuso** (reenvio de token já rotacionado revoga a família inteira).
  - Refresh token enviado **somente via cookie httpOnly, secure, sameSite=strict,
    path=/api/v1/auth** (nunca em body/query).
  - Middleware custom `verifyToken()` valida `Authorization: Bearer` com `jwt.verify`
    (`jose`, RS256) e checa `tokenVersion` contra Redis a cada request.
- **[S2] Dependências novas a adicionar** (F1): `jose` (JWT RS256), `bcryptjs` (hashing),
  `zustand` (store), `ioredis` + `@types/ioredis` (Redis tokenVersion/rate-limit), `axios`
  (interceptor), `resend` (provedor de email transacional da issue #3). `@auth/core` typings
  se necessário.
- **[S3] Divisão de rotas** (ADR-009/010): `/api/auth/*` = interno Auth.js (fixo, existente);
  `/api/v1/auth/*` = REST custom (módulo novo). Não re-implementar OAuth em `/api/v1/auth/*`.
  **Há dois fluxos de magic link, propositalmente distintos e NÃO conflitantes:**
  (a) o `EmailProvider` do Auth.js em `/api/auth/callback/email` (Sprint 0, sessão JWT do
  Auth.js) e (b) o REST `POST /api/v1/auth/magic-link{,-verify}` (tasks 9/10, que emitem a
  Custom JWT Layer). Não mesclar; cada um guarda seu token em `VerificationToken`
  (`type = MAGIC_LINK`) e segue seu próprio contrato.
- **[S4] Senha** (RNF-AUTH-002): `bcryptjs` custo **12**. Validação de senha: min 8 chars,
  1 maiúscula, 1 minúscula, 1 número, 1 especial (RF-AUTH-001).
- **[S5] Rate limiting** (RNF-AUTH-004) persistido em **uma fonte**: `docs/07-security/permissions.md`.
  Login 5/15min (ADMIN 20/15min); cadastro 3/IP/h; magic link 3/h; reset 3/h; verificação 1/min.
- **[S10] Serviço compartilhado de tokens** (DRY, F2+): toda emissão/renovação de access+refresh
  passa por um único serviço **`src/services/token-service.ts`** (path fixo — sem alternativa)
  com: `signAccessToken(user)` (jose RS256, 15min, `{sub,role,plan,tokenVersion}`),
  `createRefreshSession(user, {userAgent, ip})` (grava `Session` com `tokenHash`/`familyId`),
  `rotateRefresh(token)` (rotação+reuso), `verifyAccessToken(bearer)` (valida RS256 + `tokenVersion`
  contra Redis). `login`/`magic-link/verify`/`refresh`/OAuth-callback **reutilizam** o serviço —
  nunca duplicar a lógica de rotação.
- **[S6] LGPD soft-delete** (`docs/solutions/patterns/security/soft-delete-gdpr-window.md`):
  filtros usam `AND isActive = true AND deletedAt IS NULL`; janela 30 dias; hard delete/anônimo
  após 30 dias; restauração dentro da janela. Anti-enumeração: DELETE/account e magic-link
  retornam 200 idêntico independente do resultado.
- **[S7] providerId convention**
  (`docs/solutions/patterns/security/providerid-normalization-convention.md`): EMAIL → e-mail
  minúsculo; GOOGLE/FACEBOOK → OAuth subject ID.
- **[S8] Erros com prefixo `AUTH_*`** e códigos HTTP documentados em `04-api/authentication.md` §Códigos de Erro.
- **[S9] Validação server-side com Zod** em todas as rotas `/api/v1/auth/*` (RFC: design §7.5).
- **[S11] Contrato canônico de `/api/v1/auth/register`** (resolve divergência 04-api vs design §3):
  - Seguir **design §3** (RF-AUTH-001/005): body `{ name, email, password, passwordConfirmation,
    acceptTerms }` — **sem `birthDate`/`AUTH_UNDER_AGE` no MVP** (mantido para evolução de perfil);
    resposta **201** = `{ user: { id, name, email, emailVerified }, message }` — **sem
    `accessToken`/`meta`** (o cadastro NÃO faz auto-login; exige verificação de email —
    RF-AUTH-005 "acesso completo só após verificação").
  - Erros: `400 VALIDATION_ERROR`, `409 AUTH_EMAIL_ALREADY_EXISTS`, `422 VALIDATION_ERROR`
    (validação de negócio). Divergência com a 04-api registrada p/ doc-shepherd (F7-término).
- **[S12] `emailVerified` é `DateTime?`** (`prisma/schema.prisma:40`, design §4) — **não boolean**:
  - No DB/API: valor é `Date | null` (data da verificação). No frontend (AuthStore, design §5),
    derivar `emailVerified: boolean` como `user.emailVerified !== null`.
  - T30 grava `emailVerified = new Date()`; T25/T19 usam a derivação booleana.

## Technical Considerations

- **ORM discipline (Prisma):** qualquer mudança de schema (F1 tasks 4/5; F5 se precisar coluna
  de hard-delete/anônimo) segue a skill `typeorm`/`prisma` — **generate → drift-check → run
  localmente IMEDIATAMENTE** (chain atômica). `migration_lock.toml` já é `postgresql`.
- **Redis para `tokenVersion`:** sem Redis não há revogação imediata (ADR-009 Gate B/ADR-010
  negativa). Esta é a razão de a **Custom JWT Layer completa com Redis** ter sido escolhida.
  Redis também serve de back/blacklist dos refresh tokens e store de rate limiting (F7).
- **`jose` por Edge-compat:** usar `jose` (não `jsonwebtoken`) para RS256 no Edge/proxy.
- **Email (Resend, task 3):** provedor transacional. O fluxo magic link do Auth.js (Sprint 0)
  usa `nodemailer` + SMTP; a issue #3 troca/formaliza para **Resend** com **template
  transacional**. Manter compat com o guard dev `AUTH_EMAIL_SKIP_SEND=true`.
- **Segurança (security-sentinel):** CSRF double-submit nos endpoints com cookie
  (design §7.1); nunca logar password/token (Pino redact já existe em `src/lib/logger.ts`);
  `.env.example` com `AUTH_*`/`SMTP_*`/`REDIS_URL`; tokens só no header `Authorization`/cookie.
- **Observability (C13):** respostas de erro do `src/app/api/v1/auth/*` incluem `requestId`
  (correlação, `meta.requestId`); log estruturado de eventos de segurança (falha de login,
  reuso de refresh, soft-delete, bump de `tokenVersion`, rate-limit atingido) via
  `src/lib/logger.ts`; métricas de rate-limit por rota. Embedded em T7a/T13/T27 — sem task nova.
- **Soft-delete:** `deletedAt` nullable já existe; nenhum backfill necessário. Consultas devem
  usar `AND isActive = true AND deletedAt IS NULL`.
- **Anti-enumeração:** magic-link e forgot-password retornam 200 idêntico para email existente
  ou não (RF-AUTH-003/004).
- **Frontend (design §1):** componentes com Zod client-side, react-hook-form, shadcn/ui já
  presente (`src/components/ui/*`), tokens/tema já configurados (globals.css). Layout 50/50
  com imagem temática e Framer Motion (animação entrada 300ms) — Framer Motion é **nova dep**
  para F6.
- **Textos:** mensagens de erro ao usuário em pt-BR (projeto), código/log em inglês por
  convenção do projeto.
- **Testes:** `vitest` (config em `vitest.config.ts`, `tests/**/*.test.ts`), mocks via
  `vi.mock("@/lib/prisma")` (padrão em `tests/auth.test.ts`). E2E Playwright é dep nova (F7).
- **Rate limiting em memória** (task 27) é o fallback do Gateway; com Redis escolhido, o
  rate limiting deve usar **Redis** (servidor único/aplicável multi-instância), mantendo o
  contrato de status 429 descrito nas rotas.
- **NFR RNF-AUTH-001 (P95 < 500ms):** operações de auth (login, cadastro, verificação, logout)
  devem responder < 500ms P95 em carga normal. Guia de implementação: usar o cache Redis p/
  `tokenVersion` (T7a) e rate-limit (T27) fora do caminho crítico de DB; evitar joins pesados
  nas consultas de login/refresh; mensurar em testes de carga leves na F7.

## Acceptance Criteria

Fluxos principais (draft do spec-flow-analyzer; ACs finais por task nas issues):

#### AC-1: Cadastro com email/senha (RF-AUTH-001) — Must-have
**Given** um visitante na página `/register` com dados válidos (nome 2–50, email único,
senha 8+ com maiúscula/minúscula/número/especial, confirmação idêntica, `acceptTerms=true`)
**When** ele submete o formulário
**Then** a conta é criada (bcrypt custo 12), email de verificação é enviado, e a resposta é
201; reenviar o mesmo email retorna 409 `AUTH_EMAIL_ALREADY_EXISTS`.

#### AC-2: Login com email/senha (RF-AUTH-001/002 path custom) — Must-have
**Given** um usuário ativo com credenciais válidas
**When** ele chama `POST /api/v1/auth/login`
**Then** recebe access token (15min) no body + refresh token (30d) em cookie httpOnly
`path=/api/v1/auth`; credenciais erradas → 401 `AUTH_INVALID_CREDENTIALS`; 5 falhas/15min → 429.
Credencial válida com email **não verificado** → `401 AUTH_EMAIL_NOT_VERIFIED` (C9).

#### AC-3: Refresh com rotação e detecção de reuso (RF-AUTH-006) — Must-have
**Given** um usuário com refresh token válido (`Session.tokenHash`)
**When** ele chama `POST /api/v1/auth/refresh` com o cookie
**Then** recebe novo access + novo refresh (mesmo `familyId`, `replacedByTokenId` setado no
anterior); reenviar o token já rotacionado revoga **toda a família** (`familyId`).

#### AC-4: Magic link (RF-AUTH-003) — Must-have
**Given** um usuário digita o email em `POST /api/v1/auth/magic-link`
**When** ele clica no link com o token dentro de 15 minutos
**Then** o token é consumido (single-use) e o usuário autentica; token expirado → 410
`AUTH_MAGIC_TOKEN_EXPIRED`; reenviar o mesmo token → 401 `AUTH_MAGIC_TOKEN_INVALID`;
>3 solicitações/h ⇒ 429. Resposta de envio é 200 idêntica para email existente ou não.

#### AC-5: Recuperação de senha (RF-AUTH-004) — Must-have
**Given** um usuário solicita reset
**When** ele usa o token (1h) e define nova senha
**Then** a senha é atualizada, os tokens de sessão são invalidados e um log de segurança é
emitido; token inválido/expirado → 401 `AUTH_RESET_TOKEN_INVALID`.

#### AC-6: Logout (RF-AUTH-007) — Must-have
**Given** um usuário autenticado
**When** ele chama `POST /api/v1/auth/logout`
**Then** o refresh token é revogado (removido), cookies de auth são limpos, e o store Zustand
é zerado; suporta "logout de todos os dispositivos".

#### AC-7: Deleção de conta LGPD (RF-AUTH-008) — Must-have
**Given** um usuário autenticado digita `DELETE /api/v1/auth/account` com email da conta
**When** a confirmação confere
**Then** soft-delete (`deletedAt`+`isActive=false`), conta inacessível, resposta 200 idêntica;
após 30 dias o job de hard delete/anônimo remove dados pessoais; dentro da janela o endpoint
de restauração reverte. Anti-enumeração: mensagem idêntica em qualquer caso.

#### AC-8: Proteção de rotas (RF — AuthGuard/roteamento) — Must-have
**Given** um usuário não autenticado (ou com access expirado sem refresh válido)
**When** ele acessa `/dashboard` (ou rota protegida)
**Then** é redirecionado para `/login`; com access válido, vê a rota; `requiredRole` bloqueia
perfis sem permissão.

    `passwordConfirmation` idêntico, `acceptTerms === true`); hash bcrypt custo 12
  - `201 { user: { id, name, email, emailVerified }, message }` | `409 AUTH_EMAIL_ALREADY_EXISTS`
    | `422 VALIDATION_ERROR`; cria `User` com `role=USER`, `plan=FREE`, `provider=EMAIL`,
    `providerId=email lowercase`; envia email de verificação (24h)
- [ ] T7 [US1] Implement `POST /api/v1/auth/login` em `src/app/api/v1/auth/login/route.ts`
