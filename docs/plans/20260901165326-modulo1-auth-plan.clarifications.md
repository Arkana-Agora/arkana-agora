## Session 2026-09-01

- Q1 — Onde vive a fonte-da-verdade do `tokenVersion` (o `User` model atual não tem a coluna;
  o ADR-009 diz que a claim é validada contra Redis a cada requisição; bump em role/plan,
  suspensão, logout-all)?
  - Recommendation: Coluna no `User` + Redis como cache (mais durável e auditável).
  - **Final Answer: Coluna no `User` (`tokenVersion Int @default(0)`) + Redis como cache
    espelhado p/ leitura rápida.**
  - Impact on Plan: T4 (schema) adiciona `tokenVersion Int @default(0)` ao `User`; T5
    (migration) inclui a coluna; T7a (`verifyAccessToken`) valida contra o cache Redis que
    espelha a coluna; T27 confirma Redis (Upstash) p/ multi-instância.

- Q2 — O que acontece com a guarda de rotas do MVP (`src/proxy.ts` +
  `src/app/(app)/layout.tsx`, via `getToken({ secret: AUTH_SECRET })`) quando a Custom JWT
  Layer passa a ser a sessão real (F4/T8) e F6/F7 trazem AuthGuard/AuthStore?
  - Recommendation: Migrar p/ access token (validar o access RS256 via token-service).
  - **Final Answer: Fase 4 migra a guarda MVP de `getToken` (Auth.js) p/ validação do access
    token (RS256 via token-service da F2); F6/F7 (AuthGuard/AuthStore) assumem sobre isso.**
  - Impact on Plan: nova decisão de solução sobre integração F4→F6 (a taxa `src/proxy.ts` +
    layout guard passam a validar o access token; `/api/auth/*` fica só p/ callbacks).

- Q3 — `tasks.md` não lista task para `POST /api/v1/auth/verify-email` (RF-AUTH-005 / design
  §3), mas a task 6 envia o email de verificação. Adicionar task de consumo do token ao plano
  ou deixar p/ issue futura?
  - Recommendation: Adicionar task extra **T30** (Fase 3).
  - **Final Answer: Adicionar task T30 — `POST /api/v1/auth/verify-email` (single-use, 24h;
    `type=EMAIL` literal no `VerificationToken` — conforme schema/design §4; expirado → 410
    `AUTH_EMAIL_VERIFY_EXPIRED`; inválido → 401 `AUTH_EMAIL_VERIFY_INVALID`; marca
    `User.emailVerified = new Date()` e aumenta `tokenVersion`).**
  - Impact on Plan: nova task T30 na Fase 3 + Master Checklist; fecha o ciclo
    cadastro→verificação→login (acopla com a task 6, que usa `type=EMAIL` 24h).

- Q4 — A issue #8 diz "Google/Facebook OAuth", mas o MVP só ativa Google (ADR-010). Escopo da
  task 8?
  - Recommendation: Apenas emissão de tokens custom no callback, sem implementar Facebook.
  - **Final Answer: Task 8 = emissão de tokens custom no callback (Google + magic link);
    Facebook fica fora da Sprint 1.**
  - Impact on Plan: mantém "Out of scope" e o escopo da T8 (nenhuma mudança de provedor).

- Q5 — Qual plataforma de deploy para (a) job agendado de hard delete (T16) e (b) Redis em
  staging/prod (tokenVersion + rate limit)?
  - Recommendation: Vercel Cron + Upstash Redis (padrão p/ Next.js no Vercel, custo zero de
    infra extra).
  - **Final Answer: Vercel Cron p/ o job de hard delete (T16) + Upstash Redis p/ staging/prod
    (tokenVersion + rate limit).**
  - Impact on Plan: T16 documenta Vercel Cron (`vercel.json`/cron route); T27 usa `ioredis`
    apontando p/ Upstash; `.env.example` inclui `REDIS_URL`.

## Session 2026-09-01 (2)

- Q6 — RF-AUTH-005: o que acontece ao fazer login (email/senha) de conta com email NÃO
  verificado? (afeta T7 login, T19 form, T25 store; AuthStore deriva `isAuthenticated` de
  `emailVerified`).
  - Recommendation: Bloquear com código próprio de erro (`AUTH_EMAIL_NOT_VERIFIED`).
  - **Final Answer: Login com credencial válida e email não verificado → `401
    AUTH_EMAIL_NOT_VERIFIED` (auth parcial); cliente redireciona p/ `/auth/verify-email`;
    store: `isAuthenticated=false`, user parcial persistido p/ permitir reenvio.**
  - Impact on Plan: T7 adiciona o código no caso de `emailVerified == null`; T19 trata o erro
    e redireciona; T25 guarda user parcial; novo item de codificação no catálogo `AUTH_*` +
    doc-shepherd na 04-api.

- Q7 — design §6 lista rotas de UI `/auth/verify-email` (VerifyEmailPage) e
  `/auth/callback/magic-link` (MagicLinkCallback), mas tasks T18–T24 não as incluem. Sem elas,
  os fluxos verify-email (T30/Q6) e magic link REST (T9/T10) não têm página.
  - Recommendation: Adicionar as duas páginas como task extra.
  - **Final Answer: Adicionar task T31 (Fase 6): VerifyEmailPage (`/auth/verify-email`, com
    resend e callback de token) + MagicLinkCallback (`/auth/callback/magic-link`, redime via
    `POST /magic-link/verify` e redireciona ao dashboard).**
  - Impact on Plan: nova task T31 na Fase 6 + Master Checklist + rota de UI em design §6.

- Q8 — design §7.3: lockout por falhas consecutivas (403 `AUTH_ACCOUNT_LOCKED`, retryAfter 900)
  e rate-limit (429 5/15min) aparecem no mesmo endpoint de login sem relação definida.
  - Recommendation: Lockout de conta (403) + rate-limit de IP (429) independentes.
  - **Final Answer: Falhas consecutivas disparam lockout de conta → `403 AUTH_ACCOUNT_LOCKED`
    (retryAfter 900) ANTES do limite de IP; o rate-limit de IP (429) é mecanismo independente
    de volume. Ambos cobertos (T7).**
  - Impact on Plan: T7 especifica a prioridade (consecutive-failure lockout por email → 403;
    volume IP → 429); sem duplicar os códigos no plano.

- Q9 — No fluxo Google OAuth (T8/loginWithGoogle), o user criado via OAuth deve exigir
  verify-email no frontend ou ser considerado verificado?
  - Recommendation: Auto-verificar Google (email confirmado pelo provedor).
  - **Final Answer: OAuth Google é **auto-verificado**: `emailVerified` tratado como verificado
    no callback (RF-AUTH-002/ADR-010), sem exigir verify-email; guard/loginWithGoogle permite
    acesso normal. (A regra C6/Q6 aplica-se a credentials.)**
  - Impact on Plan: T8 especifica que o callback marca/skipar verificação no fluxo OAuth; T25
    `loginWithGoogle` não passa pela tela de verificação.

- Q10 — Gaps de observability (OBS-006/009): rastreabilidade (requestId) nas respostas de erro
  e alertas/instrumentação p/ eventos críticos (reuso de refresh, falhas de login).
  - Recommendation: Embedded nas tasks existentes (sem task nova).
  - **Final Answer: Observability **embedded** nas tasks de backend: `requestId` + correlação
    nas respostas de erro (meta.requestId), log estruturado de eventos de segurança (falha de
    login, reuso de refresh, soft-delete, bump de tokenVersion) e métricas de rate-limit
    atingido — dentro de T7a/T13/T27 + doc-shepherd (04-api/security).**
  - Impact on Plan: nota nas Technical Considerations + reforço em T7a/T13/T27; sem nova task.

## Session 2026-09-04 (T8)

- Q11 — Como a Custom JWT Layer recebe os tokens custom no fluxo OAuth/magic link do Auth.js
  (o MVP só tem o cookie de sessão JWT do Auth.js; o Schéma de sessão JWT não carrega tokens)?
  - Recommendation: Callback emite + session expõe o access token (storage só após redeem no
    frontend; sem tokens na URL).
  - **Final Answer: Callback emite + session expõe token (C14):** no callback `jwt`, após
    identidade confirmada (Google OAuth `/api/auth/callback/google` ou magic link
    `/api/auth/callback/email`), `emitCustomTokens()` dispara a emissão da Custom JWT Layer via
    `signAccessToken` (`{ id, role, plan, tokenVersion }`) + `createRefreshSession(userId, {})`,
    numa única guarda de idempotência (`!token.customAuth`); o callback `session` expõe
    `session.accessToken` (lido pelo AuthStore da T25). O wrapper
    `src/app/api/auth/[...nextauth]/route.ts` (`finalizeAuthResponse`) define o cookie
    `refreshToken` httpOnly (`Path=/api/v1/auth`, `SameSite=Strict`, `Max-Age=30d`) e rescreve o
    redirect final para `/dashboard`, **sem tokens na URL** (design §2). Google permanece
    auto-verificado (C12): o callback marca `emailVerified = new Date()` quando `null`.
  - Impact on Plan: T8 implementa os callbacks `jwt`/`session` + wrapper da rota; T25 lê
    `session.accessToken` p/ popular a AuthStore; design §2 "OAuth Google/Facebook e Magic Link"
    atualizado com o fluxo de emissão no callback (substitui a menção de middleware `verifyToken`).
